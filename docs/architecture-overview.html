要点：

  • 两种 Agent Runtime 形态对 server 协议透明：本机 multica daemon 与云端 node 都走同一套 register / claim / heartbeat / task，差别只在本机还是 EC2。
  • 正确性靠 HTTP claim，不靠 WS。WS 唤醒只是"可能有活"的提示，真正抢占是 POST /tasks/claim，保证多 daemon / 多 server 实例下任务不重复执行。
  • events.Bus 是中枢：task 终态、progress、评论变更都进 Bus，再分发给 daemon WS 投递和 realtime 浏览器广播。

3. Realtime 多实例 Redis Relay

单机部署时 realtime 直接进程内广播；多实例部署时引入 Redis Stream 分片 relay，保证任一 server 实例发出的帧所有实例的订阅者都能收到。

flowchart TB subgraph Pods["Server 实例 ×N"] P1["Pod A<br/>realtime.Hub"] P2["Pod B<br/>realtime.Hub"] P3["Pod C<br/>realtime.Hub"] end subgraph Redis["Redis"] direction LR S0["shard 0<br/>ws:relay:shard:0"] S1["shard 1<br/>ws:relay:shard:1"] S2["...<br/>shard N"] S7["shard 7<br/>ws:relay:shard:7"] end Clients["浏览器订阅者<br/>散布在各 Pod"] P1 -->|"XADD (按 hash 选 shard)"| S0 P1 -->|"XADD"| S3["shard 3"] P2 -->|"XADD"| S1 P3 -->|"XADD"| S7 P1 -->|"XREADGROUP 阻塞读<br/>所有 shard, RecallGrace 回看"| S0 P1 --> S1 P2 --> S0 P2 --> S7 P3 --> S1 P3 --> S3 P1 -->|"本地 Hub 广播"| Clients P2 -->|"本地 Hub 广播"| Clients P3 -->|"本地 Hub 广播"| Clients

机制要点（见 sharded_stream_relay.go / redis_relay.go）：

  • 固定 8 个 shard，key ws:relay:shard:N；发布按 hash(scopeID) % shards 选 shard。
  • 每个 Pod 起所有 shard 的阻塞 reader —— 任意 Pod 发的帧，所有 Pod 都能读到并广播给本地订阅者。
  • reader 启动从 (now - ReplayGrace) 回看，保证 Pod 重启期间漏掉的帧能补播；stream 有 MAXLEN 上界，下游消费必须幂等。
  • 本地 Hub 端有 event-id 去重，同一帧不会被重复推给同一订阅者。

4. Agent Runtime 单次任务调用时序

这是"用户给 issue 指派 agent → agent 真的跑起来 → 结果回到前端"的完整时序，最值得反复对照。

sequenceDiagram autonumber participant U as 用户 Web/Desktop participant S as Server HTTP API participant T as issueTrigger + TaskService participant E as events.Bus participant DW as daemonws.Hub participant RT as Realtime /ws → 浏览器 participant D as 本机 Daemon participant B as agent.Backend participant CLI as AI CLI 子进程 U->>S: 改 issue: assignee=agent, status=启动 S->>T: issueTrigger.dispatchIssueRun T->>T: EnqueueTaskForIssue (写 task, 绑定 runtime_id) T->>E: task.assigned E->>DW: NotifyTaskAvailable(runtimeID, taskID) DW->>D: daemon:task_available (WS 唤醒) D->>S: POST /api/daemon/runtimes/{rid}/tasks/claim S-->>D: 200 Task{prompt, repo, skills, model, mcp, local_dir} D->>S: POST /tasks/{id}/prepare-lease (抢占期续租) D->>S: POST /tasks/{id}/start (标记 running) D->>D: runTask: 解析 repo 克隆 / skills bundle / local-dir / env D->>B: Backend.Execute(ctx, prompt, ExecOptions) B->>CLI: spawn claude/codex/copilot/cursor/... --mcp-config ... loop 流式产出（并行心跳） CLI-->>B: text / thinking / tool-use / tool-result 事件 B-->>D: Message 流（channel） D->>S: POST /tasks/{id}/progress {step,total} D->>S: POST /tasks/{id}/messages S->>E: task.progress / task.message E->>RT: 广播到 workspace scope 订阅者 RT-->>U: WS 推送 → React Query patch 缓存 end D->>D: idle watchdog: 语义停活跃度判定，kill 长静默 alt 正常完成 D->>S: POST /tasks/{id}/complete {output, branch, session, workdir} D->>S: POST /tasks/{id}/usage {per-model tokens} D->>S: POST /tasks/{id}/session (pin resume 指针) else 失败/超时/取消 D->>S: POST /tasks/{id}/fail {err, failureReason} end S->>E: task.terminal E->>RT: 广播 issue 状态/评论变更 RT-->>U: WS 推送 → 前端 invalidate/patch

关键点：

  • 唤醒 → claim 是两步：WS 唤醒只让 daemon 去轮询，claim 才原子地把 task 标给这个 runtime。
  • prepare-lease 是 claim 之后、start 之前的抢占保护期，runTask 启动慢（克隆 repo、装 skills）时靠它续命，防止被另一个 daemon 抢走。
  • 流式事件双向出：CLI 的每条事件既走 daemon 回报（progress/messages）进 events.Bus，又由 realtime /ws 推给浏览器，所以前端能看到 agent 在干啥。
  • resume 指针：POST /tasks/{id}/session 在完成时 pin 住 session，下次同 issue 再触发可 resumeSessionID 续跑。

5. Daemon 主循环子阶段

multica daemon start 后 Daemon.Run 是一个长生命周期循环，由若干子循环并发构成。

flowchart TB Start([multica daemon start]) --> Preflight["preflightAuth<br/>续期 PAT + 首次 workspace 同步"] Preflight --> Register["registerRuntimesForWorkspace<br/>POST /daemon/register (每 ws)"] Register --> Ready([d.ready = true]) Ready --> LoopA["workspaceSyncLoop<br/>周期拉 /api/workspaces, 新 ws 触发 register"] Ready --> LoopB["heartbeatLoop<br/>WS 心跳 + HTTP fallback, 续租 runtime 在线"] Ready --> LoopC["tokenRenewalLoop<br/>PAT 到期前续期"] Ready --> LoopD["wakeup / reconcile<br/>runTaskWakeupConnection 监听 WS 唤醒"] Ready --> LoopE["taskRunner 池<br/>MaxConcurrentTasks 个 slot"] Ready --> LoopF["GC / 孤儿回收<br/>recover-orphans, workdir 清理"] Ready --> LoopG["auto_update / model-list 报告"] LoopD -->|"task_available"| LoopE LoopE --> runTask["runTask<br/>claim → prepare-lease → start → Execute → report"] subgraph Fallback["WS 不可用时的降级"] LoopB -.->|"心跳无 ack"| HBhttp["HTTP POST /daemon/heartbeat"] LoopD -.->|"WS 断线"| Poll["定时 POST /tasks/pending 轮询"] end

设计取舍：

  • WS 优先、HTTP 兜底：心跳和任务唤醒都优先走 WS，丢 ack 才回退 HTTP，降低 server 负载又不丢正确性。
  • task slot 池：MaxConcurrentTasks 控制并发，每个 slot 独立跑一次 runTask；claim 失败（被抢/无任务）就回睡眠等下一轮唤醒。
  • 孤儿回收：daemon 重启或崩溃前正在跑的 task，靠 recover-orphans 把它们标记回 pending，避免永久卡死。

6. Agent Backend 统一抽象

server/pkg/agent 把 16 种编码 CLI 收敛成一个 Backend 接口，runTask 只对接这个接口 —— 加新 CLI 不动调度链。

  • agent.New(type) 按 SupportedTypes 白名单选具体后端；白名单与 DB runtime_profile.protocol_family CHECK 约束同源。

7. Cloud Runtime 开通与回连

云端 node 不是另一套协议：server 只代理 fleet 管理 node 生命周期，node 起来后自带 daemon 用 node-scoped mcn_ PAT 回连，对 server 完全透明。

sequenceDiagram autonumber participant U as 用户 participant S as Server /api/cloud-runtime/* participant F as Fleet API (multica-cloud) participant EC2 as 云端 node / EC2 participant S2 as Server (同上, 回连侧) participant DW as daemonws.Hub U->>S: POST /cloud-runtime/nodes (开通) S->>F: POST /api/v1/nodes (转发, 带 X-User-ID) F->>F: 签发 node-scoped mcn_ PAT F->>EC2: SSM bootstrap 注入 mcn_ PAT + daemon F-->>S: node 元信息 S-->>U: node 列表 / 状态 U->>S: POST /cloud-runtime/nodes/start S->>F: POST /api/v1/nodes/start F->>EC2: 启动实例 EC2->>S2: POST /api/daemon/register (mcn_ PAT) EC2->>S2: WS /api/daemon/ws (注册 runtime) S2->>DW: 索引到该 node 的 runtime Note over EC2,S2: 之后与本地 daemon 完全同构:<br/>claim → runTask → Execute → report DW->>EC2: daemon:task_available 唤醒 EC2->>S2: POST /tasks/claim EC2->>EC2: spawn AI CLI 子进程 EC2->>S2: progress / complete / usage

安全取舍（见 cloud_runtime.go / cloudruntime/client.go）：

  • server 不转发用户的 mul_ PAT 给 fleet，node 用自己独立的 mcn_ PAT 回连，单 node 被攻破不波及用户长期凭证。
  • server 对 fleet 的调用全程带 X-User-ID / X-Request-ID，并有 op 维度的请求指标（provision / terminate / status / gateway）。
  • node 回连后走完全相同的 daemon 协议，所以前文时序图对云端 node 同样成立。

8. 关键交互点速查

交互 端点 / 通道 方向 用途
浏览器订阅 WS /ws server → 浏览器 task/issue/chat 实时推送
Daemon 注册 POST /api/daemon/register daemon → server 上报 runtime 列表/模型/skills
Daemon 心跳 POST /api/daemon/heartbeat + WS daemon ↔ server 续租在线态, 兜底降级
任务唤醒 daemon:task_available (WS) server → daemon "可能有活"的提示
任务抢占 POST .../tasks/claim daemon → server 原子认领, 唯一执行者
进度回报 POST .../tasks/progress /messages daemon → server 流式状态回到 events.Bus
终态回报 POST .../tasks/complete /fail /usage daemon → server 结束 + token 统计
Cloud 开通 POST /api/cloud-runtime/nodes server → fleet 起 EC2 node
Cloud 回连 POST /api/daemon/register (mcn_ PAT) node → server 回连成普通 daemon

一句话总结架构：前端走 REST + /ws 看结果，daemon 走 REST + /api/daemon/ws 干活，两者由 events.Bus + Redis relay 串起来；agent 真正执行是 daemon 用统一 Backend 接口 spawn 本机 / 云端 CLI 子进程，云端 node 只是把同一套 daemon 协议搬到了 EC2。
